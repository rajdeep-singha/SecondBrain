## 2. 🟠 `MAX_JOB_RETRIES` config is silently ignored

## 3. 🟠 SSRF: `validateURL` allows internal/metadata targets
`http/handlers/scraper.go:386` only checks the scheme is http/https and the host is non-empty. A request for `http://169.254.169.254/latest/meta-data/`, `http://localhost:8080/`, or a private-range IP will be fetched by the server. For any hosted/multi-tenant deployment this is a classic SSRF vector. **Fix:** block loopback, link-local, and private ranges (resolve host, reject `IsPrivate()`/`IsLoopback()`/`IsLinkLocalUnicast()`).

## 4. 🟠 Batch parent can flip to "completed" prematurely
`store/memory.go:104` and `store/postgres.go:41` mark the parent `completed` (setting `CompletedAt`/`DurationMs`) as soon as no child is pending/processing. But `CreateBatchJob` inserts+submits children **one at a time** in a loop — a fast worker can finish child #1 before child #2 is inserted, so `total==1, pending==0` → parent marked done, then reverts to `processing`. Emits a bogus completion + duration. **Fix:** create all child rows first, then submit; or track expected child count on the parent.

## 5. 🟡 `Pool.Submit` blocks the HTTP request goroutine under load
`worker/worker.go:60` — the comment says "Non-blocking if buffer has space," but it's a bare `p.jobs <- msg`. When the buffer (`JOB_BUFFER_SIZE`, default 100) fills, `CreateJob`/`ScrapeSync`/batch handlers block instead of returning a fast 429/503. ## 6. 🟡 Converter content-quality gaps

## The issue

The pool has two knobs: `WORKER_POOL_SIZE` (default **5**) goroutines draining a buffered channel of depth `JOB_BUFFER_SIZE` (default **100**). So the system absorbs ~105 jobs (100 queued + 5 in-flight), and each job can run up to `JobTimeout` (**120s**).

```go
// worker.go:60
func (p *Pool) Submit(msg models.JobMessage) {
	p.jobs <- msg   // blocks when the buffer is full
}
```

When job #106 arrives while all 5 workers are busy *and* the buffer is full, `p.jobs <- msg` **blocks the Fiber request goroutine** that called it (`CreateJob`, `ScrapeSync`, or `CreateBatchJob`). Consequences:

1. **No fast failure** — the client's HTTP request just hangs (until a worker frees a slot, or the client/socket times out). The comment "Non-blocking if buffer has space" quietly omits what happens when it *doesn't*.
2. **Pile-up** — under sustained overload, more request goroutines stack up blocked on the send, holding connections/memory, with no `Retry-After` or 503 to tell clients to back off.
3. **Worst for `ScrapeSync`** — it blocks *before* it even starts polling, so the request's own timeout logic never engages.

There's also a **subtlety** the fix must handle: all three handlers `CreateJob` in the store (status `pending`) **before** submitting. That ordering is required — the worker calls `UpdateStatus` and expects the row to exist. So if we shed load by rejecting the submit, we must also mark that just-created row failed, or it becomes a permanent `pending` zombie.

## The fix

Make `Submit` a non-blocking try-send returning `bool`; on rejection, callers return **503 + `Retry-After`** and mark the orphaned job failed. The 100-deep buffer already absorbs bursts, so a full buffer is a genuine overload signal — shedding is correct.
