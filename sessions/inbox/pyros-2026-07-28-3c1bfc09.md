**claude:** Here's an accurate picture of what "agent coordination" actually means in pyros, so you can talk about it without overclaiming. There are **two distinct coordination stories** in this codebase — keep them separate when you speak, because they're often conflated.

## 1. One agent orchestrating many deterministic tools (the core story)

Pyros is not a chat model with a robotics prompt. It's a **ReAct agent** (`src/pyros/agent/react.py`) running a `Think → Act → Observe → Loop`, conducting ~73 *deterministic* engineering tools (`kinematics`, `inverse_kinematics`, `size_actuator`, `select_controller`, `select_planner`, `power_budget`, `generate_bom`, …).

Talking points:
- **"The LLM reasons; the tools compute."** The model decides *which* tool and *why*; the numbers come from deterministic, catalog-grounded, cited engineering code — not from the model's guesses. That's the whole design premise (`README.md:13`).
- **Three coordination modes over one brain** (`src/pyros/agent/modes.py`): **Act**, **Plan**, **Diagnose**. All three share a single robotics knowledge core (`robotics_brain.py`), so the agent carries full domain knowledge regardless of mode — the mode only shapes *how* it sequences tools.
- **Nested orchestration**: a high-level call like `run("fix workspace")` internally fans out to `validate_urdf → fix_urdf → ci`. One agent action coordinates a pipeline of sub-tools.

## 2. Inter-agent coordination via MCP (the interoperability story)

Pyros ships an **MCP server** (`src/pyros/mcp/server.py`, entry point `pyros-mcp`) that exposes every primitive to *any external agent* — Claude Desktop, Cursor, Windsurf, Claude Code.

Talking points:
- **Pyros becomes a specialist another agent coordinates with.** A generalist coding agent hits a robotics problem, delegates to pyros' tools, and reasons over the results. Pyros is the "engineering brain" the host agent doesn't have.
- **Coordination needs contracts, not prose.** Every tool returns JSON-serializable dicts with a stable `schema_version: "1.0"`, no ANSI, no chat text (`server.py` header). That's the deliberate design choice that makes agent-to-agent handoff reliable.
- **Provider-agnostic tool-calling**: there's a JSON text-protocol path (`react.py:_render_tools_for_text`) so even API-key-less CLI bridges can drive the same tools — the coordination layer isn't locked to one model's native tool API.

## What to *avoid* claiming
This codebase is about **agent↔tool** and **agent↔agent** coordination for robot *design*. I did **not** find any multi-robot **fleet/swarm runtime** coordination (agents commanding multiple physical robots in the loop). If someone asks about swarm/fleet control, be honest that that's not what this is — the "coordination" here is orchestrating an engineering toolchain and interoperating with other AI agents.
