## What "agent coordination" means in PYROS *today*

PYROS is currently a **single-agent, many-tool orchestrator** — not a multi-agent system yet. Worth being precise about this because it's exactly the gap your talking points can frame:

- **One ReAct agent loop** (`src/pyros/agent/react.py`) — Think → Act → Observe — drives ~73 deterministic engineering tools (`size_actuator`, `compute_dynamics`, `select_controller`, `generate_ros2_control`, …).
- **Three *modes* of that one agent** (`modes.py`): Act / Plan / Diagnose. These are modes, not separate agents.
- **MCP server** (`src/pyros/mcp/server.py`) exposes the same tools so *external* agents (Claude Desktop, Cursor, Windsurf) can call them. That's the only "multi-agent" surface today — other agents borrowing PYROS's brain.

So "coordination of agents" is genuinely a **future direction**, and that's a strong thing to present.

## Your MuJoCo vs Gazebo workspaces — the key fact

The simulator picker (`src/pyros/sim/runner.py`, `_select_backend`) chooses **exactly one backend per run — never both**:

| | MuJoCo backend | Gazebo backend |
|---|---|---|
| Nature | in-process, **10–100× faster** | full ROS2 fidelity (native or Docker) |
| Good for | contact-rich dynamics, PID/RL tuning loops, `needs_speed` | sensors, topics, Nav2, whole-system integration, `needs_ros2_topics` |

The routing is: user-specified → else ROS2 topics needed → Gazebo → else speed → MuJoCo → default MuJoCo.

### "Is there a model where you need BOTH?"

Yes — and you already have the workspaces for the best examples. The industry-standard pattern is **tune in MuJoCo, validate in Gazebo**:

1. **Humanoid / bipedal** (`current workspace/humanoid_bipedal_robot_ws`) — tune the balance & gait controller in MuJoCo (fast, contact-rich, thousands of tuning iterations), then validate the full ros2_control + perception stack in Gazebo. This is the cleanest "needs both" story.
2. **Warehouse mobile manipulator** (`warehouse_mujoco_sim` + `industrial_robotic_arm_ws`) — grasp/arm contact dynamics tuned in MuJoCo; Nav2 + lidar/camera perception validated in Gazebo.
3. **Aerial drone** (`aerial_drone_ws`) — flight-control tuning fast in MuJoCo; PX4/ROS2 topic + sensor integration in Gazebo.

The talking point: *PYROS's own tuning engine (`TuningEngine`) already runs closed-loop against MuJoCo for speed — the natural next step is a "handoff" that promotes a tuned controller into a Gazebo integration run.* Today nothing bridges the two backends; that bridge is a compelling feature to propose.

## "Any robot where multiple agents are needed to build from my workspace?"

Two valid readings, both good talking points:

**(a) Multiple *engineering* sub-agents building ONE robot** (division of labor over the shared `WorkspaceGraph`):
- Mechanical/kinematics agent (`compute_kinematics`, `analyze_workspace`, `compute_ik`)
- Actuation agent (`static_torques`, `compute_dynamics`, `size_actuator`, `power_budget`)
- Controls agent (`select_controller`, tuning loop)
- Perception/Nav agent (sensors, Nav2)
- Simulation agent (MuJoCo/Gazebo)

The robot that *justifies* this is a **mobile manipulator** (your `industrial_robotic_arm_ws` on a mobile base): the arm team and base team must agree on interfaces — the ros2_control "zero-drift" contract and a consistent TF tree — which is exactly the coordination problem multi-agent systems solve.

**(b) Multi-*robot* systems** — a warehouse fleet (multiple AMRs + arms) where PYROS builds each robot's workspace and validates the shared DDS/QoS and TF across the fleet.
